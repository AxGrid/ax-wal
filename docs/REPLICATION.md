# Репликация ax-wal

Как держать копию WAL на соседнем сервере: какие есть режимы, как их включать, что происходит при сбоях и как переключаться на копию.

## Режимы

| Режим | Что это | Когда брать |
|---|---|---|
| **Реплика, асинхронная** | Точная копия только для чтения: те же номера записей, что на мастере. `Append` на мастере не ждёт реплику. | По умолчанию. Копия отстаёт на миллисекунды; при гибели диска мастера теряется неотправленный хвост. |
| **Реплика, синхронная** | То же, но `Append` возвращается только после того, как реплика записала запись на свой диск. При проблемах со связью мастер сам уходит в асинхронный режим и сам возвращается. | Когда подтверждённая запись не должна пропасть вместе с диском мастера. |
| **Зеркало (`Mirror`)** | Перекладывает записи из одного WAL в другой обычным писателем. Номера записей могут не совпадать, каталог назначения доступен на запись. | Перенос, перешифрование, сборка нескольких источников. Не резервная копия. |
| **Зеркало из архива** | Догоняет локальный каталог по объектам в B2 / S3. | Копия без доступа к боевому серверу. Отстаёт на время ротации и выгрузки сегмента. |

Дальше — про реплику. Зеркала описаны в `README.md`.

## Как устроена реплика

```
мастер                                   соседний сервер
┌────────────────────┐                  ┌──────────────────────────┐
│ сервис (Writer)    │                  │ axwal-mirror -replica    │
│ axwal-serve / Serve│◄── SSH-туннель ──│   пишет /srv/wal-replica │
│   127.0.0.1:9001   │                  │ читатели (Reader)        │
└────────────────────┘                  └──────────────────────────┘
```

- На мастере сетевую точку открывает `axwal-serve` (или `axwal.Serve` внутри сервиса). Она слушает `127.0.0.1`, наружу не торчит.
- Реплика сама поднимает SSH-соединение с мастером и ходит к этой точке через туннель. Отдельный `ssh -L` не нужен.
- При каждом подключении реплика просит записи «с моего последнего номера + 1». Что у неё есть, решает её собственный каталог, а не память мастера, поэтому после обрыва или перезапуска нет ни пропусков, ни дублей.
- Мастеру реплика подтверждает запись только после того, как та легла на её диск.

## Включение: асинхронная реплика

### 1. Мастер

Отдельным процессом рядом с сервисом:

```bash
axwal-serve -dir /var/wal -listen 127.0.0.1:9001
```

Либо внутри сервиса, который пишет WAL:

```go
go axwal.Serve(ctx, axwal.ServerOptions{
    Dir:    "/var/wal",
    Listen: "127.0.0.1:9001",
})
```

Если на мастере включён retention, поднимите `Retention.StaleReaderTTL` (по умолчанию 60 с) до самого долгого простоя реплики, который хотите пережить — см. раздел «Расхождение».

### 2. Соседний сервер

```bash
axwal-mirror -replica \
    -tunnel root@primary.example.com:22 \
    -ssh-key ~/.ssh/id_ed25519 \
    -ssh-known-hosts ~/.ssh/known_hosts \
    -addr 127.0.0.1:9001 \
    -dst /srv/wal-replica \
    -name replica-1
```

| Флаг | Значение |
|---|---|
| `-replica` | режим точной копии только для чтения |
| `-tunnel user@host[:port]` | SSH-сервер мастера; порт по умолчанию 22 |
| `-ssh-key`, `-ssh-key-pass` | приватный ключ и пароль к нему |
| `-ssh-agent` | брать ключи из `SSH_AUTH_SOCK` |
| `-ssh-known-hosts` | файл `known_hosts`; без него ключ хоста **не проверяется** |
| `-addr` | адрес `axwal-serve`, как его видит мастер (обычно `127.0.0.1:9001`) |
| `-dst` | каталог реплики; при первом запуске пустой или отсутствует |
| `-name` | имя реплики на мастере; должно быть постоянным |

Без `-tunnel` реплика идёт на `-addr` напрямую по TCP — для WireGuard или закрытой сети. Шифрования и авторизации в самом протоколе нет, поэтому по открытой сети — только через SSH.

Из кода:

```go
err := axwal.RunReplica(ctx, axwal.ReplicaOptions{
    Dir: "/srv/wal-replica",
    Source: axwal.RemoteReaderOptions{
        Addr: "127.0.0.1:9001",
        Name: "replica-1",
        SSHTunnel: &axwal.SSHTunnelConfig{
            Host:           "primary.example.com:22",
            User:           "root",
            KeyFile:        "/root/.ssh/id_ed25519",
            KnownHostsFile: "/root/.ssh/known_hosts",
        },
    },
    Writer: axwal.WriterOptions{CompressOnRotate: true}, // настройки локального WAL
})
```

`RunReplica` работает, пока не отменён `ctx`. Запускать под systemd или другим супервизором.

## Включение: синхронная реплика

Реплика запускается так же, как асинхронная. Меняется только мастер, и здесь есть жёсткое условие: **сетевая точка должна работать в том же процессе, что и писатель** — иначе подтверждения от реплики до писателя не дойдут. Отдельный `axwal-serve` синхронный режим не даёт.

```go
w, err := axwal.OpenWriter(axwal.WriterOptions{
    Dir: "/var/wal",
    SyncReplication: &axwal.SyncReplicationConfig{
        Timeout: time.Second,
    },
})

go axwal.Serve(ctx, axwal.ServerOptions{
    Writer: w,                 // связывает сервер с писателем
    Listen: "127.0.0.1:9001",
})
```

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `Timeout` | 1 с | сколько `Append` готов ждать реплику, прежде чем писатель уйдёт в асинхронный режим |
| `RecoverLag` | 1000 записей | при каком отставании реплики синхронный режим включается обратно |
| `Cooldown` | 5 с | минимум времени в асинхронном режиме после отката по таймауту, чтобы медленная связь не вызывала дёрганье |

### Как он себя ведёт

- **Реплика на связи.** `Append` возвращается, когда запись на диске мастера и на диске реплики. Ожидание идёт вне блокировки писателя: несколько одновременных `Append` делят один сетевой круг.
- **Реплика не ответила за `Timeout`.** Писатель переключается в асинхронный режим. Эта одна запись возвращается успешно через `Timeout`, следующие не ждут вообще. Ошибок нет: локально всё записано, реплика продолжает получать поток.
- **Реплика отключилась.** Переключение в асинхронный режим сразу, без ожидания таймаута.
- **Реплика догнала.** Когда отставание не больше `RecoverLag` и после отката по таймауту прошёл `Cooldown`, писатель сам возвращается в синхронный режим.
- **Реплики нет вообще.** Писатель просто асинхронный.

### Что это гарантирует

Пока `Stats().SyncReplicationActive == true`, каждая подтверждённая запись есть на двух машинах. Записи, сделанные в окне отката, лежат только на мастере, пока реплика не догонит. Так же устроен semi-sync в MySQL.

Цена в синхронном режиме — к каждой записи (или группе одновременных) добавляется сетевой круг и fsync реплики. `AppendAsync` реплику не ждёт в вызывающем коде: ждёт фоновая горутина, которая разбирает очередь.

## Что происходит при сбоях

| Событие | Поведение |
|---|---|
| Соединение оборвалось, мастер или sshd перезапущен | Реплика переподключается с паузой от 1 до 30 с и догоняет со своего последнего номера. |
| Связь умерла молча (данные просто перестали идти) | Мастер пингует простаивающие соединения. Если реплика ничего не слышит дольше `IdleTimeout` (60 с), она рвёт соединение и подключается заново. |
| Реплика вернулась, а мастер считает старое соединение живым | Новое соединение вытесняет старое с тем же именем. |
| Реплика перезапущена | Продолжает со своего последнего номера. |
| Мастер уже удалил записи, нужные реплике | Реплика останавливается с `ErrReplicaDiverged`. См. ниже. |
| Реплика оказалась впереди мастера | То же, `ErrReplicaDiverged`. |

Параметры переподключения в коде: `ReplicaOptions.Reconnect` (пауза), `RemoteReaderOptions.IdleTimeout` и `DialTimeout`.

### Расхождение

Курсор реплики (`-name`) удерживает retention мастера, пока её heartbeat свежее `Retention.StaleReaderTTL`. Если реплика лежала дольше и мастер успел удалить сегменты, которые она не получила, дыру закрыть нечем. Реплика в этом случае не продолжает с пропуском, а останавливается с ошибкой; её данные остаются нетронутыми.

Выход: залить реплику заново с пустого каталога, либо, если мастер потерян, сделать её основной (`promote`).

## Чтение с реплики

Каталог реплики — обычный WAL для читателей:

```go
r, err := axwal.OpenReader(axwal.ReaderOptions{Dir: "/srv/wal-replica", Name: "analytics"})
```

`Next` блокируется на хвосте и получает записи по мере их прихода с мастера. Работают `axwal-cli ls / stats / dump / tail`.

Чтобы читать реплику по сети или повесить на неё следующую реплику, поднимите на ней `axwal-serve -dir /srv/wal-replica`.

Писать в каталог реплики нельзя: в нём лежит файл-маркер `REPLICA`, и `OpenWriter` возвращает `ErrReplicaDir`. Это касается и `axwal-cli restore`, и обычного `axwal-mirror`.

## Переключение на реплику

Когда мастер потерян:

1. Остановить процесс реплики (`axwal-mirror -replica`).
2. Снять режим только для чтения:
   ```bash
   axwal-cli promote -dir /srv/wal-replica
   ```
   Из кода — `axwal.PromoteReplica(dir)`. Пока реплика работает, команда откажет.
3. Направить сервис на этот каталог. Нумерация продолжится с последней реплицированной записи.

Обратного превращения в реплику нет: бывший мастер после восстановления заливается как новая реплика с пустого каталога.

## Наблюдение

`Writer.Stats()` на мастере (заполняется, когда `Serve` запущен с `Writer`):

| Поле | Смысл |
|---|---|
| `ReplicasConnected` | сколько реплик подключено |
| `ReplicaAckedIndex` | до какой записи реплика подтвердила запись на диск; `LastIndex - ReplicaAckedIndex` — отставание |
| `SyncReplicationActive` | сейчас записи ждут реплику |
| `SyncReplicationFallbacks` | сколько раз писатель уходил в асинхронный режим |
| `SyncReplicationWaits` | сколько вызовов ждали реплику |

Стоит повесить оповещение на `SyncReplicationActive == false` дольше нескольких минут и на рост отставания.

На реплике `axwal-mirror` раз в `-status` (5 с) пишет в лог текущий последний номер. Переходы между режимами и переподключения логируются на обеих сторонах.

## Особенности

- **Шифрование.** Записи копируются как есть, в зашифрованном виде. Реплике ключ не нужен; читателям реплики нужны те же ключи, что на мастере.
- **Файлы сегментов.** Реплика режет сегменты по своим настройкам ротации. Совпадают номера и содержимое записей, а не имена файлов.
- **Архив и реплика** закрывают разные сбои: реплика — свежие записи и быстрое переключение, архив — долгую историю. Архиватор можно включить и на реплике через `ReplicaOptions.Writer.Archive`.
- **Версии.** Мастер нужно обновить вместе с репликой. Сервер версии 0.2.0 и старше не понимает запрос «начать строго с номера N»; реплика с ним работает, пока позиции совпадают, а при расхождении остановится с ошибкой.
- **Проверено** автотестами (обрывы, молчаливый обрыв, перезапуски, SSH-сервер внутри теста, расхождение, promote, синхронный режим с откатом и возвратом). С настоящим sshd на другой машине и на реальной сети не проверялось.
